## Project status

This is a fresh `create-next-app` scaffold (App Router, TypeScript, Tailwind v4). Only the default
`app/layout.tsx` and `app/page.tsx` exist — no LINE webhook route, no Supabase client, no bot logic
has been written yet. `@line/bot-sdk`, `@supabase/supabase-js`, and `@supabase/ssr` are already
declared in `package.json` as the intended stack, so new work should build the integration using
these rather than introducing alternative libraries.

## Commands

- `npm run dev` — start the Next.js dev server (http://localhost:3000)
- `npm run build` — production build
- `npm run start` — run the production build
- `npm run lint` — ESLint (flat config via `eslint.config.mjs`, extends `eslint-config-next`)

There is no test runner configured in `package.json` yet.

## Next.js version caveat

`next` is pinned to `16.3.8`, newer than most training data. Per `AGENTS.md`, read the relevant
page under `node_modules/next/dist/docs/` (`01-app/`, `02-pages/`, `03-architecture/`, `04-community/`)
before relying on remembered Next.js APIs/conventions — behavior may have changed. One concrete
example already present in this codebase: `app/layout.tsx`'s `RootLayout` takes a typed
`LayoutProps<"/">` prop instead of the `{ children: React.ReactNode }` pattern seen in older Next.js.

`AGENTS.md`'s banner block is regenerated by `next dev` on every run (see
`node_modules/next/dist/server/lib/generate-agent-files.js`); it's expected to show as a diff, and
committing it is what keeps the tree clean.

## Architecture notes

- **Router**: App Router only (`app/` directory). No `pages/` directory exists.
- **Styling**: Tailwind CSS v4 via `@tailwindcss/postcss` (no `tailwind.config.*` file — v4 is
  CSS-first, configured through `app/globals.css`).
- **Fonts**: Geist Sans/Mono loaded via `next/font/google` in `app/layout.tsx`.
- **Path alias**: `@/*` maps to the repo root (`tsconfig.json`).
- Intended but not yet implemented: a LINE Messaging API webhook (likely an App Router Route
  Handler, e.g. `app/api/line/webhook/route.ts`) using `@line/bot-sdk`, backed by Supabase
  (`@supabase/supabase-js` / `@supabase/ssr`) for persistence/auth. The Supabase MCP server is
  enabled for this project (`.claude/settings.local.json`).

## Security rules (from the parent directory's CLAUDE.md, applies here too)

- Never hardcode API keys/tokens/credentials in source. Load all secrets from environment
  variables (e.g. `process.env.LINE_CHANNEL_ACCESS_TOKEN`, `process.env.LINE_CHANNEL_SECRET`,
  Supabase URL/keys).
- Don't commit `.env*` files (already covered by `.gitignore`) or any service-account/credential
  JSON files.
- Wrap each external API call (LINE, Supabase) in its own error handling so one failing call
  doesn't take down the whole request/handler.

## Sister-project conventions (shared with mitsumori-app)

This project shares a Supabase project with `mitsumori-app` (same org, project `xvzhjxockwommtwwfhjy`)
and follows the same coding conventions:

- App Router + TypeScript + Tailwind.
- Supabase access via `@supabase/ssr` on the client/server-component side. Server-only privileged
  access (e.g. the LINE webhook) uses a dedicated service-role client (`lib/supabase/service.ts`),
  never the anon key.
- RLS is not sufficient by itself — always pair `enable row level security` + policies with
  explicit `grant`/`revoke` on the table for the relevant role. Don't rely on default Postgres
  grants.
- Forms must prevent double submission: disable the submit control for the duration of the
  in-flight request (e.g. a `isSubmitting` state driving `disabled`), not just after success.
- New tables for this bot (`faq`, `menus`, `conversations`, etc.) must not alter or weaken
  existing `mitsumori-app` tables (`clients`, `documents`, `document_items`, `hearing_responses`,
  `job_applications`, `profiles`, `user_settings`, `app_settings`).

## LINE webhook rules

- Every request to the LINE webhook route **must** be signature-verified with
  `validateSignature` (from `@line/bot-sdk`) against the raw request body and the
  `x-line-signature` header **before** any event is processed. An invalid/missing signature must
  short-circuit with `400` — never trust the payload first and verify later.

## Confidence-scoring prompts

When writing a prompt that asks the model to self-rate confidence (e.g. "based on the FAQ, how
confident are you in this answer?"), always give concrete, checkable criteria for the low end
instead of letting the model grade itself leniently — e.g. "FAQ に該当する記述が無い場合は確信度を
5以下にする" rather than just "確信度を0〜10で答えて". Vague scales trend toward inflated
self-reported confidence.
